= TEP-1017: Advanced Chart of Accounts

Advanced Chart of Accounts specifications: support for temporal settings
per-account (open / close time specification, and support for multiple time
spans).

Github issue: https://github.com/tackler-ng/tackler/issues/154


== Description

Today `accounts.toml` is a flat list of account names. Under
`kernel.strict = true` an account is in one of two states: it is in the list
(always valid for any txn date) or it isn't (always invalid). There is no
temporal dimension.

That makes it impossible to retire an account cleanly. Removing it from
`accounts.toml` breaks strict-mode parsing of every historical txn that still
references it, because Tackler reads the current `accounts.toml`, not the
`accounts.toml` that existed on the txn's date. Tackler does not time-travel
through git during validation. Keeping the name in the list forever is the
only practical workaround, and it leaves no signal that the account has been
retired.

Opening is fine today: at parse time Tackler reads the current
`accounts.toml`.

A first-class close mechanism is also a de-facto convention in the broader
plain-text-accounting ecosystem (Beancount has a journal `close` directive;
hledger uses tags + `hledger check`; commercial bookkeeping tools
universally implement "archive, don't delete" for accounts that have been
used). Bringing this into Tackler removes the need for app-layer wrappers to
invent their own archived-accounts sidecar.

This TEP proposes per-account lifecycle and metadata expressed in
`accounts.toml`, not as journal directives. Semantically Tackler cannot
attach temporal directives to the txn stream because txn filters can drop them
out of view.


== Summary of Changes

[WARNING]
====

Support for mixed-type arrays is added to `accounts.toml`. Each `accounts`
item declares either a plain old account name (`String`) or an Account
Specification (`AccountSpec`).

Sub-changes:

* New `AccountSpec` element type for `accounts` arrays in `accounts.toml`
* Accounts with temporal validity definitions
** Per-account `open` and `close` times (half-open interval `[open, close)`)
** Per-account list of open-close pairs (spans)
* Strict-mode enforcement of temporal settings; relaxed mode is unchanged
* TBD: Reports and exports respect declared periods


=== Sub-change 1: Support for mixed-type array of `accounts`

This change add support for TOML's
https://toml.io/en/v1.1.0#array[mixed-array] format. This is a backward
compatible change, e.g.  current accounts.toml definitions are still valid
after this change.

.mixed-array example of accounts.toml
----

accounts = [
    # plain account name: unchanged behavior, always open
    "Income:Salary",
    {
        # Account Specification: account with single, fully defined '[)' validity period
        name = "Income:Salary:Acme·Inc",
        open = 2025-01-01,  # this is optional, if missing, then open from the beginning of time
        close = 2026-01-01, # this is optional, if missing, then open 'til the end of time
    },
    {
        # Account Specification: only name is specified, account is always open
        name = "Expenses:Food",
    },
    {
        # Account Specification: sporadic open with time spans
        name = "Expenses:Tax",
        spans = [
            # both open and close must be defined
            { open = 2025-01-01, close = 2025-01-31 },
            { open = 2026-01-31, close = 2026-01-31 },
        ],
    },
    {
        # Account Specification: account with sub-date precision
        name = "Expenses:New·Years·Eve:Fireworks",
        open = 2025-01-01 00:00:00,  # with time, timezone offset is based on configured default
        close = 2026-01-01 02:00:00+02:00, # with time and offset
    },
]
----

=== Sub-change 2: `open` and `close` timestamps

`open` (optional, TOML date, datetime or datetime with offset)::
First valid transaction time to have postings to this account. If `open` is
missing, then implicit value (`-infinity`) is used (the account has always
been open).  Postings to the account with txn timestamp before  `open` cause
an error in strict mode.


`close` (optional, TOML date, datetime or datetime with offset)::
First invalid transaction time for postings to this account. If `close` is
missing, then implicit value (`+infinity`) is used (the account will be close
forever, starting from that time). Postings at or after this time cause an
error in strict mode.

Together they define a half-open interval `[open, close)`. Both fields
accept the same temporal forms Tackler already accepts in txn headers:

* **Bare date** (`2023-12-31`) - normalized the same way a bare date
  is normalized in a txn header (configured time and timezone are used).
  This is the expected form for the common case, account closes "on a day."
* **Local datetime** (`2023-12-31T14:30:00`) - likewise normalized
  the same as in a txn header (configured timezone is used).
  Use when sub-day precision matters  (e.g. system cutovers,
  exchange go-live times, audit-grade events).
* **Offset datetime** (`2023-12-31T14:30:00+02:00` or `…Z`) - used
  as-is.

The existing timestamp conventions are reused, so an `open` / `close` value
behaves identically to a txn timestamp written in the same way.

It also keeps forward compatibility: writing `close = 2023-12-31` today
and later changing systems configured sub-day precision cut-off time
(configured default time) is no-cost operation, and it won't change the
internal temporal logic of journal (e.g. moving the cut-off time from midnight
to midday), it's just single setting change.

Above can be supported natively with TOML datetime type.


=== Sub-change 3: Periods via repeated entries

A spans e.g. (array of open-close pairs) is allowed and
represent disjoint periods for that account. A posting to an account
is valid only if its txn time falls into some declared time span.

This temporal time span mechanism supports following use cases:
* sporadic opens, e.g. seasonal accounts
* close-then-reopen

No nested spans are allowed, and spans are also not allowed with
account's main open-close definitions.

Implementation: sort by `open` and validate non-overlap.
Lookup could be optimized as binary search by date if needed.


=== Sub-change 4: tree-aware temporal definitions

Child account inherits temporal definition from parent, if parent have one.

In following example, accounts `a` and `a:b` are always open.
Account `a:b:c` has temporal definition,  which is inherited by `a:b:c:d`
and `a:b:c:d:e`. All of these three accounts have temporal definition
`open = 2026-01-01`, `close = 2026-01-02`.

[source, toml]
----
accounts = [
    "a",
    "a:b",
    {
        name = "a:b:c",
        open = 2026-01-01,
        close = 2026-01-02,
    },
    "a:b:c:d",
    "a:b:c:d:e",
]
----

Both parent and child can not have a temporal definition. In other words,
there can be only one temporal definition from the root to the leaf for
the account.

=== Validation rules

This rules are enforced once, at config load time.

* Same name in two `accounts = [...]` entries -> error
* Multiple `spans` items with *overlapping* periods -> error
* Multiple `spans` items with *disjoint* periods -> allowed
  This is the periods feature, Sub-change 3.
* Any `open >= close` pair -> error.

=== Future Plans and Postponed (PP) Features

==== Postponed (PP) Features

The new transaction metadata `# kind: ...` is only reserved,
not parsed as valid input by this TEP.

===== Sub-change 5: `kind` attribute

This change is postponed for separate TEP.

`kind` (optional, `"debit"` | `"credit"`)::
The account's natural balance side. Optional everywhere; if unset, no
constraint. Cascades down the account tree: subaccounts inherit the
nearest declared ancestor's `kind` unless they declare their own.

We deliberately do *not* import a 5-type plain-text-accounting taxonomy
(asset / liability / equity / income / expense). Tackler today does not
parse account types from the `Assets:` / `Income:` prefix - those are
convention, not semantics - and importing a taxonomy in this TEP invents
structure for no current consumer. The future P&L work (TEP-1003) may
want categorization with different splits; if so it adds an orthogonal
`category` field later without conflicting with `kind`.

The two-value `kind` is the minimum that supports the posting-level
override outlined in #154 (Sub-change 5) and avoids importing a
taxonomy this TEP would not be the right place to define.


===== Sub-change 5: Reserved `# kind: <value>` posting kindness override

The motivation for `kind` on accounts is enabling *corrective transactions
on immutable journals*: a posting that flips the natural debit/credit side
of its account (e.g., crediting a normally-debited asset for a refund
correction).

This TEP *reserves* the `# kind:` transaction metadata
syntax for that purpose but does *not* specify enforcement semantics
(when it errors, what changes in reports).

Architecture Decision Records::
Reserve txn metadata # kind: for latter use, with possible value # kind: revert. +
+
A use case for that would be a corrective transaction, when account kindness is enforced (credit, debit). +
+
ADR: https://github.com/tackler-ng/tackler/issues/162[GH #162]

Transaction metadata `# kind: <value>`::
This TEP reserves the syntax (Sub-change 5). When it errors and what it
changes in reports belong in a dedicated follow-up TEP focused on corrective entries.

Per-account `commodity` constraint::
Explicitly owned by xref:tep-1001.adoc[TEP-1001 - Units and Commodities]: Phase 2, which
already lists "default commodity per account?" as planned work.

Booking method (Beancount-style FIFO / LIFO / STRICT)::
Defer until lots / cost-basis exist in Tackler.

Cron-style sporadic period syntax::
Repeated `AccountSpec` blocks already cover sporadic / seasonal
accounts with explicit dates. If verbosity becomes a real complaint
later, add sugar (`every-q1 = true` or similar) then. The repeated-
entries mechanism is the underlying model regardless.
